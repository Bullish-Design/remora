# Companion Refactor — Assumptions

> **CRITICAL RULES:**
> - **NO SUBAGENTS** — Do ALL work directly.
> - **NEVER STOP AFTER COMPACTION** — Resume immediately.

---

## What "First-Class" Means

The companion demo currently lives in `remora_demo/companion/` — explicitly a demo, not part of the core system. Making it "first-class" means:

1. **It uses core remora primitives** — EventStore, SubscriptionPattern, SubscriptionRegistry, `_FrozenEvent`-based events. No parallel implementations.
2. **It lives in `src/remora/companion/`** — importable as `remora.companion`, shipped as part of the package.
3. **Its events are real `RemoraEvent`s** — persisted in EventStore, replayable, auditable.
4. **Its subscriptions use `SubscriptionPattern`** — declarative, persistent, dynamically registerable.
5. **Its workspace operations go through EventStore** — workspace writes become events, reads are projections.

---

## What "Remora Ethos" Means

From `docs/EventBased_Concept.md` and the core implementation:

1. **EventLog is the single source of truth** — Every state change is an immutable event in SQLite. No in-memory-only state that matters.
2. **Reactive, subscription-based routing** — Events trigger agents via declarative `SubscriptionPattern` matching, not manual if/elif routing.
3. **AgentNode is the single agent model** — No subclasses. Specialization via data (extension configs, extra_subscriptions, custom_system_prompt).
4. **No isinstance in business logic** — Pattern matching and duck typing only.
5. **Agents communicate through events, not direct calls** — Message passing via EventStore, not method invocations.
6. **Emergent behavior from simple rules** — Each agent is small and focused; complex behavior emerges from event cascades.

---

## What Companion Is

An ambient knowledge work assistant that:
- Tracks cursor position in Neovim
- Extracts context from code and markdown
- Searches for related content via embeddings
- Synthesizes insights from multiple tiny agents
- Composes a continuously-updated sidebar

The sidebar isn't generated by one agent — it **emerges** from 13+ agents writing to shared workspace state.

---

## Constraints

1. **177 existing tests must keep passing** (or be intentionally migrated to new imports/APIs)
2. **Behavioral equivalence** — After refactor, the companion must produce the same outputs given the same inputs
3. **No new external dependencies** — Use what's already in pyproject.toml
4. **TDD throughout** — Every change starts with a failing test
5. **Incremental** — Each phase should leave tests green; no big-bang rewrite
6. **The companion agents are NOT code-node agents** — They don't correspond to functions/classes in source code. They're functional/service agents. The refactor must accommodate this.

---

## Key Architectural Tension

Core remora agents are **code-node agents**: each maps to a discovered code entity (function, class, method, file). AgentNode has fields like `source_code`, `start_line`, `file_path`, `caller_ids` — all code-node concepts.

Companion agents are **functional agents**: cursor_tracker, context_extractor, embedding_searcher, sidebar_composer, etc. They don't correspond to code nodes. They're more like microservices in a reactive pipeline.

This tension is the central design question for the refactor. See `DECISIONS.md` for the resolution.

---

## Audience

- **Primary**: The remora project itself — companion should be a showcase of how to build on top of core remora primitives.
- **Secondary**: Developers building similar reactive agent systems who want to see how non-code-node agents can participate in the event system.

---

## Non-Goals

- Not adding new companion agents (that's a separate project)
- Not changing the LSP server or Neovim plugin (those are integration layers)
- Not refactoring the indexing/embedding system (orthogonal concern)
- Not adding LLM calls to companion agents (they're currently pure logic; that's intentional)
